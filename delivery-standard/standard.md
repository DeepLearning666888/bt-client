# 单人项目交付规范

版本 1.0 · 生效 2026-10-27 · 正文为唯一权威来源，HTML 为渲染版

---

## 1 范围

**1.1** 本规范适用于无第二人参与评审、审计、测试的软件项目全周期。

**1.2** 不适用于有 QA / CM 独立角色的团队项目。那类项目应使用组织既有体系，本规范的裁剪逻辑对它们过松。

**1.3** 本规范只保留 4 个硬卡点。依据：单人可长期维持的流程开销上限约为有效工作时间的 10%，超出则必然整体弃用——不是逐渐减少，是一次性废止。故凡不能压缩进 4 个卡点的检查项，一律降为推荐条款（SHOULD），不阻塞交付。

**1.4** 推荐条款不进入判定脚本。判断依据：一条规则如果没人执行也没人发现，它就不该写在规范里充数。

---

## 2 术语

| 术语 | 定义 |
|---|---|
| 工作单元 unit | 一次可独立验收的改动集合，通常对应一个模块或一个功能点 |
| 卡点 gate | 必须通过才能进入下一阶段的判定点，二元结论 |
| 验收标准 AC | 一条可判定的完成条件，编号 AC-nn，必须携带判定方式 |
| 证据 evidence | 由命令产出、可独立打开核对的文件 |
| 偏离 exception | 跳过某卡点的显式决策，须登记 |

---

## 3 设计依据

五条。每条对应一种已实际发生的失效，不是原则口号。

**3.1 可证伪（P1）**
判定只有「通过 / 不通过」两态。禁用「基本可用」「已完成 80%」「差不多」。
理由：程度描述无法被任何人（包括三个月后的自己）事后核对，等于没有判定。

**3.2 机器判定（P2）**
所有卡点由脚本给出结论，人不给自己签字。
理由：自证偏差。本项目实证——natdiag 交付清单中 4 处代码行数由人工填写，4 处全部错误（`collector.cpp` 126→实际 132、`serialize.cpp` 261→263、`test_collector.cpp` 189→197、`test_diagnosis.cpp` 148→147），最终靠 `wc -l` 才纠正。人工记账的可靠性不取决于认真程度，取决于有没有校验回路。

**3.3 证据生成（P3）**
证据由命令产出，人不手写。
理由：手写证据与事实之间没有约束力，写错了不会被发现。参见 3.2 的实证。

**3.4 分级适用（P4）**
按影响面分三档，每档只走必要卡点。
理由：流程疲劳。把全套流程套在改一行文案上，结果是连代码改动也一起绕过。

**3.5 偏离留痕（P5）**
允许跳过卡点，但必须登记原因与补做计划。
理由：理想化规范必然被放弃。100% 遵守率在单人项目中是假的；把偏离变成显式决策，比假装没有偏离可靠。连续 3 次跳过同一卡点，判定为该卡点设计有问题，应改规范而非继续违规。

## 4 分级

| 档位 | 触发条件 | 必过卡点 | 典型开销 |
|---|---|---|---|
| T0 | 只改文档、注释、文案、配置注释 | G2 | 分钟级 |
| T1 | 单文件内部逻辑，不改对外签名与数据布局 | G2 G3 | 十分钟级 |
| T2 | 新增文件 / 改公开接口 / 改数据结构 / 跨文件重构 | G1 G2 G3 G4 | 小时级 |

**4.1** 只要新增了源文件，至少 T2。

**4.2** 只要改动了对外暴露的函数签名、头文件公开部分、数据成员布局、序列化格式，至少 T2。

**4.3** 档位由人在 spec 中声明，脚本只校验该档要求的卡点是否全过。脚本不推断档位——无版本控制时（当前项目即无 git）任何推断都不可靠，不可靠的自动化比没有自动化更危险。

**4.4** 拿不准档位时按高一档处理。

## 5 卡点

四个。全部分布在「开工前」与「交付前」两个时点。

### G1 开工前 · 验收标准已声明

- **时机**：写下第一行代码之前
- **判定**：`specs/<unit>.md` 存在，且同时满足
  - 含 `## 目标`、`## 验收标准`、`## 不做范围` 三节
  - 验收标准条目 ≥ 1
  - 每条形如 `- [AC-nn] 描述 | 判: 判定方式`，缺 `判:` 即不通过
  - AC 编号无重复
- **命令**：`python delivery-standard/tools/gate.py g1 --unit <unit>`
- **失败后果**：不得开工
- **依据**：3.1。没有 `判:` 的标准不是标准，是意图。

### G2 交付前 · 构建通过

- **时机**：说「完成」之前
- **判定**：`config.toml` 中该 unit 的 `build` 命令全部退出码 0；日志落盘
- **命令**：`gate.py g2 --unit <unit>`
- **失败后果**：不得交付，不得用「部分成功」描述
- **依据**：3.2。

### G3 交付前 · 每条验收标准有证据，且证据本身是成功的

- **时机**：G2 通过之后
- **判定**（三条全中才算过）：
  1. spec 中每个 AC 编号，在 `evidence/<unit>/` 下存在同名文件 `AC-nn.*`
  2. 该文件可被 grep/diff 消费（无 BOM、无 NUL 字节）
  3. 文件首行记录的 `(exit=n)` 等于 config 中该 AC 的 `expect`（未写时按 0）
- **命令**：`gate.py g3 --unit <unit>`
- **失败后果**：未覆盖的 AC 必须移入「未验证」节；退出码不符的必须修到真过，不得改 `expect` 迁就结果
- **依据**：3.3。证据由 `gate.py gen` 产出，不手工创建。

> **第 3 条是 2026-11-03 补的。** 此前只查 1、2 两条，于是 `gen` 打出 `[FAIL] AC-01
> (exit=1)` 之后 `all` 照样报 `G3 PASS` —— 一条失败的证据和一条通过的证据，对判定器
> 来说长得完全一样，绿灯也就不构成证据。config 里的 `expect` 同样只是装饰：它只影响
> `gen` 的打印，没有任何一处读它来判定。
>
> 现在两条路径都读同一份 `expect`：`gen` 用它打印 PASS/FAIL，`g3` 用它判定。**同一条
> 规则只有一个事实来源**，才不会一宽一严。

### G4 交付前 · 未验证项已声明

- **时机**：G2 通过之后
- **判定**：spec 含 `## 未验证` 节且内容非空（可写「无」）
- **命令**：`gate.py g4 --unit <unit>`
- **失败后果**：不得交付
- **依据**：3.1。声明「没验的」是在结构上阻止把假设说成事实。

### 降级为推荐（SHOULD，不阻塞）

- 每次交付附一行改动摘要
- 每轮结束更新工作日志
- 公开接口变更在本单元 spec 中留一条记录

## 6 证据

**6.1 目录**

```
evidence/<unit>/
  G2-build.log        由 gate.py g2 自动写入
  AC-01.log           由 gate.py gen 按 config 中该 AC 的 cmd 产出
  AC-02.json
```

**6.2 编码**：一律 UTF-8。Windows PowerShell 的 `>` 与 `*>` 默认写 UTF-16LE，会导致 `grep` / `diff` / `sed` 静默返回空结果。本项目已因此静默失败两次（`engine-probe/probe-run2.log`、`natdiag/test.log`）。gate.py 内部强制 UTF-8 写盘，且拒绝把带 BOM 或含大量 NUL 字节的文件判为有效证据。

**6.3 可读性**：证据文件必须能独立打开看懂，不依赖上下文推断。

**6.4 保留**：不删除旧证据。同名覆盖时，新证据首行写入生成时间与命令原文。

## 7 偏离

**7.1** 文件：`exceptions.md`，一条一行。

**7.2** 必填字段：日期 / 单元 / 跳过的卡点 / 原因 / 补做计划。

**7.3** 不追究。但必须记。未登记的偏离视为未发生——只有在事后被发现的偏离才算问题。

**7.4** 同一卡点连续 3 次被跳过 → 该卡点设计有问题，进入规范修订流程（见 8.2）。

---

## 8 变更控制

**8.1** 正文为 `standard.md`，通过 diff 查看变更。HTML 版为渲染产物，不单独修改。

**8.2** 修订须记录：版本号 / 日期 / 改了哪条 / 触发原因。触发原因必须是可核验的事实（偏离记录编号、具体失效案例），不接受「感觉更合理」。

**8.3** 调整卡点数量、判定方式、分级门槛 → 主版本号递增（v2）。措辞澄清、示例补充 → 次版本号（v1.x）。

---

## 9 已知弱点

规范必须写清自己哪里不行，否则使用者会误判其保障范围。

**9.1 档位自评无外部约束。** 声明 T0 就走得最少，没有第二个人核对声明是否合理。缓解措施只有 4.4（拿不准按高档）和事后复核。这是本规范最大的结构性缺口，无技术解，只能靠偏离记录暴露行为模式。

**9.2 只覆盖构建与证据，不覆盖设计质量。** 一个模块可以 100% 通过四个卡点，同时架构是错的。卡点保证的是「说完成时确实能跑且有据」，不保证「做对了」。

**9.3 无版本控制支撑。** 当前项目未初始化 git，4.3 的档位声明没有任何 diff 可供交叉验证，7 的偏离也无从自动发现。建议初始化 git，但那是独立决策，不在本规范强制范围内。

**9.4 测试质量无法校验。** G3 现在能查出「命令失败」了（读退出码），但查不出「命令通过但没测到东西」。断言写 `assert(true)`、测试文件里一个用例都没跑、或者跑的全是别的模块，退出码同样是 0。这一层需要人工抽查，属于推荐条款。

## 10 与 natdiag 四栏表的关系

上一轮交付的 `natdiag-delivery-checklist.html`（工序｜标准｜清单｜判定｜证据 共 11 道工序）为本规范的前身。调整如下：

| 处理 | 内容 | 理由 |
|---|---|---|
| 保留 | 标准 / 判定 / 证据 三列 | 这三列是 G1 / G3 的内核 |
| 压缩 | 11 道工序 → 4 个卡点 | 11 道工序的实际开销远超 10%，不可持续（1.3） |
| 改造 | 清单由人整理 → 脚本生成 | 人工清单已出现 4 处事实错误（3.2） |
| 新增 | 分级（4）、偏离记录（7）、已知弱点（9） | 原版本缺裁剪机制与自限声明 |

原 HTML 作为历史交付物保留不动。

## 附录 A 快速上手

```bash
# 1. 复制模板，写验收标准（G1 的前置）
cp delivery-standard/templates/unit-spec.md specs/myunit.md
#    编辑后校验结构
python delivery-standard/tools/gate.py g1 --unit myunit

# 2. 产出证据
python delivery-standard/tools/gate.py gen --unit myunit

# 3. 按档位跑全部卡点
python delivery-standard/tools/gate.py all --unit myunit
```

退出码：`0` 全过 / `1` 有卡点不通过 / `2` 用法或配置错误。
