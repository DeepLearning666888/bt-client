单人项目交付规范 v1.0

「工序-标准-清单-证据」的精简落地 · 4 个硬卡点 · 判定全程脚本化 · 2026-10-27
4硬卡点（原 11 道工序）

它解决的那一个问题：单人项目没有第二个人签字，最大的风险不是做错，是自己给自己放行。 所以这套东西把「人审计」整个换成「脚本判定」——四个卡点全由 gate.py 出结论，证据全部由命令产出，人不参与打分。

一、上一版为什么不成立

上一轮的 natdiag 交付清单是 11 道工序 × 四栏（工序｜标准｜清单｜判定｜证据），看得出用心，但有两处硬伤：

问题实证后果
开销不可持续 11 道工序逐条整理，耗时远超有效工时的 10% 单人不可能每轮都做，最终必然整体弃用——不是逐渐减少，是一次性废止
清单靠人整理 文档里 4 处代码行数由人工填写，4 处全错：collector.cpp 126→实 132、serialize.cpp 261→263、test_collector.cpp 189→197、test_diagnosis.cpp 148→147 最后靠 wc -l 才发现。人工记账的可靠性不取决于认真程度，取决于有没有校验回路
事后整理 表格是做完之后回头补的 补的表只能自证，堵不住任何东西。卡点必须前置

二、五条设计依据

每条对应一种已实际发生的失效，不是原则口号。

编号依据解决的失效
P1可证伪
只有通过 / 不通过两态，禁用「基本可用」「已完成 80%」		程度描述无法被任何人（包括三个月后的自己）事后核对
P2机器判定
卡点由脚本给结论，人不给自己签字		自证偏差。见上表 4 处行数全错
P3证据生成
证据由命令产出，人不手写		手写证据与事实之间没有约束力
P4分级适用
按影响面三档，每档只走必要卡点		流程疲劳。全套流程套在改一行文案上，结果是连代码改动也一起绕过
P5偏离留痕
允许跳过，但必须登记原因与补做计划		理想化规范必然被放弃。100% 遵守率是假的，把偏离变成显式决策才可靠

三、四个卡点

G1　验收标准已声明开工前 · 不过则不得开工
spec 存在且含「目标 / 验收标准 / 不做范围」三节；每条 AC 形如 - [AC-01] 描述 | 判: 方式，缺判定方式即不通过；编号不得重复；残留「待填写 / TODO」即不通过。
依据 P1：没有判定方式的标准不是标准，是意图。
G2　构建通过交付前 · 不过则不得交付
config 中声明的构建命令全部退出码 0，日志落盘 evidence/<unit>/G2-build.log。
依据 P2：说「完成」之前必须真的跑过，不接受「部分成功」这种描述。
G3　每条验收标准有证据，且证据本身是成功的交付前 · 不过则未覆盖项必须移入未验证
每个 AC 编号在 evidence/<unit>/ 下存在同名文件，编码合规（拒绝带 BOM 或含 NUL 的文件）， 且文件首行记录的 (exit=n) 等于 config 中该 AC 的 expect（未写时按 0）。
依据 P3：证据由 gate.py gen 产出，不手工创建。
第三条是 2026-11-03 补的：此前只查文件在不在，于是 gen 打出 [FAIL] AC-01 (exit=1) 之后 all 照样报 G3 PASS — 失败的证据和通过的证据对判定器来说长得一样，绿灯也就不构成证据。
G4　未验证项已声明交付前 · 不过则不得交付
spec 含「未验证」节且内容非空（可写「无」）。
依据 P1：在结构上阻止把假设说成事实。

四、分级

档位触发条件必过卡点典型开销
T0只改文档、注释、文案G2分钟级
T1单文件内部逻辑，不改对外签名与数据布局G2 G3十分钟级
T2新增文件 / 改公开接口 / 改数据结构 / 跨文件重构G1 G2 G3 G4小时级

4.1 只要新增了源文件，至少 T2。4.2 只要改了对外签名、公开头文件、数据成员布局、序列化格式，至少 T2。 4.3 档位由人声明，脚本只校验该档要求的卡点是否全过——脚本不推断档位，因为本项目无版本控制，任何 diff 推断都不可靠，不可靠的自动化比没有自动化更危险。4.4 拿不准按高一档。

## 常驻负向对照单元
G1 @ __negative__  （无 spec）      → [FAIL] spec 不存在          exit=1
G2 @ __failbuild__（构建恒失败）    → [FAIL] 命令退出码 3         exit=1
这 19 项里 4 项是「应当通过」，15 项是「应当失败」。刻意混合：只有正向用例，判定器恒真也能全过；只有负向用例，判定器恒假也能全过。

六、spec 长什么样

# natdiag

## 目标
NAT 端口映射诊断模块：把引擎层 6 类 alert 归一成统一事件流。

## 验收标准
- [AC-01] 核心库单元测试全部通过 | 判: natdiag/build/natdiag-tests.exe 退出码 0

## 不做范围
- 不验收 working / refused 判定结论：本网络构造不出真实场景

## 未验证
- working / refused 判定路径无真实环境验证：仅由单测合成 alert 事件覆盖
- OpenSSL 缺失：BT 协议加密不可用，是否影响 swarm 连通性未测

判: 后面必须是可执行命令或可测量指标。写「功能正常」不算——这类表述无法核对，G1 也拦不住，只能靠写的人自己不放水。这是规范的盲区，见第九节。

九、已知弱点

规范必须写清自己哪里不行，否则使用者会误判其保障范围。以下四条都无法用本规范自身消除。
编号弱点为什么消不掉
9.1档位自评无外部约束声明 T0 就能少走卡点，没有第二个人核对声明是否合理。无技术解，只能靠偏离记录事后暴露行为模式
9.2只覆盖构建与证据，不覆盖设计质量一个模块可以 100% 通过四个卡点，同时架构是错的。卡点保证「说完成时确实能跑且有据」，不保证「做对了」
9.3无版本控制支撑当前项目未初始化 git，档位声明没有 diff 可交叉验证，偏离也无从自动发现
9.4测试质量无法校验G3 现在能查出「命令失败」（读退出码），但查不出「命令通过却没测到东西」。断言写 assert(true)、一个用例都没跑、跑的是别的模块，退出码同样是 0

十、怎么用

python delivery-standard/tools/gate.py doctor      # 环境与已声明单元
python delivery-standard/tools/gate.py gen --unit myunit    # 产出证据
python delivery-standard/tools/gate.py all --unit myunit    # 按档位跑全部卡点

退出码 0 全过 / 1 有卡点不通过 / 2 用法或配置错误。完整说明见 delivery-standard/README.md。
