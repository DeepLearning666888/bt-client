一、为什么要先出清单

上一轮我提了「把 NAT 诊断逻辑抽成模块」这一句就完了，没有文件级凭据、没有接口契约、没有验证方案。这次补上。

更关键的是：这段代码不能直接搬。我读完 314 行 main.cpp，里面混着 5 处设计缺陷。如果照搬成模块，缺陷会跟着进生产代码，而 M2 的桌面端会直接消费它的输出——那时再改就要动 UI 契约。现在改是零成本。

二、现存代码的 5 个缺陷（可核验）

#位置问题后果

三、模块边界

核心决策：模块不持有 session，不自己跑协议，只消费事件并给出结论。

引擎进程 / 探针
   │  lt::session::pop_alerts()
   ▼
natdiag::from_alert(alert)      ← 唯一接触 libtorrent 的地方
   │  NatEvent（纯数据，5 个字段）
   ▼
natdiag::Collector::feed(ev)    ← 只吃自己定义的事件，不吃 lt::alert
   │
   ▼
natdiag::Collector::snapshot()  ← 不可变快照，可反复取
   │
   ├─ natdiag::to_json()        → M2 桌面端 / HTTP 接口
   └─ natdiag::to_text()        → CLI 探针 / 日志

为什么 collector 不吃 lt::alert

为了可测性。造一个真实的 portmap_alert 需要 session 上下文和真实网关；造一个 NatEvent 只要填 5 个字段。代价是多 110 行适配代码，换来的是判定逻辑可以脱离网络做穷举测试——这对一个「结论会被用户当成故障依据」的模块是硬要求。

为什么返回快照而不是回调

诊断是状态查询，不是事件流。快照天然可序列化、可缓存、可对比，UI 拉取比订阅简单。

五、接口契约

5.1 公共头（只暴露这些）

namespace natdiag {

enum class Transport { natpmp, upnp };                    // NAT-PMP 侧含 PCP
enum class Protocol  { tcp, udp };
enum class SlotState { unmapped, pending, mapped, rejected };

enum class Verdict {
    working,        // 至少一个组合拿到映射，上传可恢复
    refused,        // 网关明确拒绝（有错误码）
    silent,         // 请求已发出，无应答 —— 本机实测就是这种
    disabled,       // 请求数为 0，协议没发出去
    insufficient    // 采样窗口太短，不敢下结论
};

enum class Remediation {
    none, manual_port_forward, check_firewall, enable_protocol, sample_longer
};

struct NatEvent {                       // 唯一的输入单元
    enum class Kind { listen_ok, listen_fail, map_ok, map_err, map_log, external_ip };
    Kind kind;
    Transport transport;                  // listen_* / external_ip 时无意义
    Protocol protocol;                    // map_log / external_ip 时无意义
    int port = 0;
    int error_code = 0;                   // 0 = 无错误
    std::string detail;                   // 已字符串化的地址 / 错误文本
};

struct SlotStateInfo {
    Transport transport; Protocol protocol;
    SlotState state = SlotState::unmapped;
    int external_port = 0;                 // 仅 mapped 有效
    int error_code = 0;                    // 仅 rejected 有效
    std::string error_text;
    int log_lines = 0;                     // 证据计数
};

struct Snapshot {
    std::vector<std::string> listen_ok;    // "TCP 192.168.1.100:6881"
    std::vector<std::string> listen_fail;
    SlotStateInfo slots[4];               // 固定 4 项，顺序稳定
    std::string external_ip;              // 不参与判定，见第二节警告
    Verdict verdict = Verdict::insufficient;
    std::vector<Remediation> remediation;
    int sampled_seconds = 0;
};

class Collector {
public:
    void feed(NatEvent const& ev);
    void set_elapsed(int seconds);       // 宿主告知已采样多久
    Snapshot snapshot() const;             // 纯函数式，不改状态
};

}  // namespace natdiag

external_ip_reliable 恒为 false 除非对应 slot 为 mapped——这是第二节那个坑的代码级防线，不是注释级约定。

slot 中不含 error_code / error_text：草案原有这两个字段，但 rejected 状态取消后它们无处安放，错误信息统一移入顶层 unattributed_errors 数组（vector，一条不丢）。差异见 12.1。

六、判定规则表（diagnosis.cpp 的规格，也是测试用例来源）

观察verdict处置建议
任一 slot 为 mappedworkingnone
存在 rejected，且无 mappedrefusedmanual_port_forward + 展示网关错误码
全部 pending，且 log_lines 总和 > 0silentmanual_port_forward（本机实测形态）
全部 unmapped 或 log_lines 为 0disabledenable_protocol
sampled_seconds < 阈值insufficientsample_longer
采样阈值标为假设值。默认取 15 秒，依据只是「比实测 60 秒窗口短」，没有协议层的重试周期数据支撑。libtorrent 的实际重试节奏要在 M1b 联调时测出来再校准。现在写成可配置常量，不写成魔法数。

八、验证方案

第一级：单元测试（不碰网络）

判定表 5 行 + 状态机 6 类边界，全部用合成事件驱动。ctest 一条命令跑完，秒级。

第二级：golden 回归（真实网络）

用同一份 Debian 种子重跑探针，结论必须与基线一致：

基线项值（probe-run2.log）允许偏差
listen socket 数6≥ 4（网络栈差异）
NAT-PMP/PCP TCP无应答必须一致
NAT-PMP/PCP UDP无应答必须一致
UPnP-IGD TCP / UDP无应答必须一致
log lines21 / 62≥ 1（数量随重试浮动）
external ip203.0.113.7允许变化（PPPoE 重新拨号）
verdictsilent必须一致
基线文件先转码再入库。probe-run2.log 是 UTF-16LE（PowerShell *> 的默认行为），grep／sed／diff 对它一律静默返回空结果——我第一次查它时就是这样，差点把「匹配不到」当成「日志里没有」。iconv -f UTF-16LE -t UTF-8 转成 probe-run2-utf8.log 后归档，之后所有比对只认 UTF-8。

第三级：行为等价性

旧二进制与新二进制在同一份输入下，verdict 与 4 个 slot 的 state 必须逐项相同。人读文本格式允许变（会加处理建议），但结论不允许变。

不做理由

十二、实现与本文档的差异（交付后补记）

先纠正本文档第二节第 2 条判断错误。我当时写「portmap_error_alert 的真实协议字段被丢弃」，这是错的。 读头文件确认：这个 alert 根本没有 map_protocol 字段，只有 mapping（per-socket 索引）、 map_transport、local_address、error。原代码写 none 是无奈，不是疏忽。
由此引出的更严重设计缺陷仍然成立，但根因不同：不是「丢字段」，而是**没有处理「协议归属本来就拿不到」这件事**——用单键 map 导致同一 transport 的多条错误互相覆盖。 我在实现中途试图用 (transport, local_address, mapping) 三元组关联表反查协议，读了 session_impl.cpp:2336 的 remap_ports()，确认每个 mapper 确实先 tcp 后 udp 注册、索引看似可推断。 但随后放弃了这个方案，理由有两条： 1. delete_mapping 之后索引是否复位**未写在文档里**，而 remap_ports 会被网络变化反复触发； 2. 产品上 TCP 还是 UDP 被拒**不改变处置动作**，用户要的是「能不能通」和「怎么办」。 于是 SlotState::rejected 与关联表一并删除。留一个永远产生不了的状态是垃圾，还会让测试出现盲区。

12.4 两个环境坑（写进 README）

bash 脚本里 fork Windows 子进程返回 127。我先用 regress.sh 写比对，两个二进制都返回 127、 日志 0 字节、无任何错误信息，排查方向一度被带到二进制本身（我单独验了 legacy.exe 是正常的）。 最后确认是 shell 沙箱限制，改 Python subprocess 后一次通过。

运行期 DLL 不能依赖 PATH。脚本继承的 PATH 混着 C:\Program Files\... 条目， 冒号被当作分隔符切碎。改用 CMake POST_BUILD 把 DLL 复制到 exe 同目录。

12.5 D-01：pending 曾是死枚举（交付后复核发现并修复）

问题：SlotState::pending 在 collector.cpp 里从未被赋值，snapshot() 只是复制。 后果两条：① 5.2 承诺的 "state":"pending" 永不出现，M2 无法区分「根本没试」和「请求在飞」； ② 判定逻辑里 state == pending 是死分支，测试对 pending 零引用——这个状态从未被验证过。

为什么漏掉：删 rejected 时我审查了状态集合，但只核对了「删掉的那个」，没有反向核对「留下的每个值是否都有产生路径」。

修复：map_log 到达时把该 transport 下 unmapped 的 slot 推进为 pending，已 mapped 的不降级。补 3 条回归用例：推进 / 不降级 / JSON 中真实出现。

验证：L1 —— 27 例 88 断言 0 失败；L2 —— golden 回归在修复后重跑仍 PASS（对外结论零变化）；L3 —— 实测四个 slot 全部输出 "state":"pending"，log_lines 19/19/55/55。

影响面：不影响既有验收结论。这是兑现已承诺的契约，不是行为变更。
