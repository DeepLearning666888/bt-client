一、这一轮到底解决了什么

M0 用 aria2 做基线，留下一个空洞：aria2 的 Windows 构建没编 UPnP，且只跑 TCP， 所以「三种自动映射全灭」这个结论其实是在一个能力不全的客户端上得出的。本轮把真正的内核 （libtorrent 2.0.11）从源码编出来并实测，把这个洞补上了。

三、对 M0 结论的两处修正

M0 原结论本轮判定依据
路由器对 SSDP 组播和单播都不响应 需修正 SSDP 发现是通的：单次运行发现 13 个 rootdevice（192.168.50.1～192.168.50.14:37443）。 失败发生在下一步——HTTP 取描述文件被 403 拒绝。原来的「不响应」是错判。
无入站则上传恒为 0 需修正 本轮上传 0.32 / 0.37 MB/s，非零。M0 那次是 aria2，可能与其配置或 peer 分布有关， 不足以支撑「无入站 = 上传恒 0」这个强结论。

另外，网络的真实形态也确认了：WLAN 是 192.168.1.100/23，掩码 /23 让 192.168.0.x 与我们处在同一个二层广播域，所以这不是双层 NAT， 而是同网段里有一批 UPnP 设备全部拒绝服务。

GET http://192.168.50.1:37443/upnpap.xml
HTTP/1.1 403 Forbidden
SERVER: Linux/5.10.0, UPnP/1.0, Portable SDK for UPnP devices/1.14.12

GET http://192.168.50.1:37443/rootDesc.xml   ->  404

设备跑的是 Linux 5.10 + pupnp 1.14.12（标准 UPnP 协议栈），说明它具备 UPnP 能力， 只是拒绝向我们提供描述文件。具体原因尚未定位（可能是源地址/授权策略），不做进一步推断。

四、工具链的坑：一条根因链

这一轮真正耗时的是 vcpkg，而它所有报错都是同一个原因的不同表现：

安全策略把 reg.exe 列入程序黑名单
  └─ vcvars64.bat 靠 reg.exe 查 SDK 安装位置 → 查不到
      └─ 它导出的 INCLUDE / LIB / PATH 全部残缺（实测快照）
           INCLUDE = 只有 MSVC\include + VC\Auxiliary\VS\include   ← 缺 ucrt/um/shared/winrt
           LIB     = 只有 MSVC\lib\x64                            ← 缺 um\x64 / ucrt\x64
           PATH    = 被整体覆盖，SDK bin、cmake、ninja 全不见
              └─ CMake 探不到 rc.exe / mt.exe → CMAKE_MT-NOTFOUND
                  └─ 编译器测试链接失败 → 所有 port 编译失败

连带症状包括：Could not fetch ninja（其实 ninja 单独跑成功）、 curl error 7 连不上 github（vcpkg 读 IE 代理也是靠 reg.exe， 读不到就直连）。都不是独立问题。

最终方案：绕开 vcpkg。手工拼 INCLUDE/LIB/PATH（等价于 vcvars 的产出，不碰注册表）， CMake + Ninja + MSVC 直接编。已固化为 engine-probe/env.cmd 与 env.ps1（后者受 PowerShell 执行策略限制，用 env.cmd）。

五、对产品的直接影响

结论依据产品动作
自动入站映射在本网络不可用 libtorrent 把 UPnP + NAT-PMP + PCP 全部试过，四条路径全断 「手动端口映射引导」是必备功能，不是可选优化
失败原因可以分类展示 三种失败模式在告警层是可区分的：未发现设备 / 设备拒绝(403) / 请求无应答 诊断面板要显示具体原因，而不是笼统的「NAT 受限」——这正是纯客户端能给出的差异化
上传不依赖入站映射 本轮上传 0.37 MB/s 时无任何映射 「上传恒 0」不能写进产品文案；做种能力的真实上限需要单独受控测
当前构建缺 OpenSSL 编译期 OpenSSL 未找到，走降级分支 上线前必须补：否则 HTTPS tracker 不可用、SSL peer 连不上
