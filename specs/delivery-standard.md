# delivery-standard

## 目标

把「工序-标准-清单-证据」这套做法改造成单人可长期维持的形态：压到 4 个卡点、判定全部由脚本给出、证据全部由命令产出。目标是让「做完了」这个结论有机器可核对的依据，而不是凭自觉。

## 验收标准

- [AC-01] 判定器自身可被 Python 解析与编译 | 判: `python -m py_compile` 退出码 0
- [AC-02] 判定器能正确报告运行环境与配置 | 判: `gate.py doctor` 退出码 0，输出包含项目根、配置路径、已声明单元
- [AC-03] 判定器对缺失 spec 的单元返回失败而非通过 | 判: `gate.py g1 --unit __negative__` 退出码为 1（负向验证，证明判定器不是恒真）
- [AC-04] 判定器对 19 类正常/异常输入给出正确结论 | 判: `gate.py selftest` 退出码 0，19/19 通过
- [AC-05] G3 拒绝「退出码与预期不符」的证据，而不是只看文件在不在 | 判: `python delivery-standard/tests/t_g3_exit.py` 退出码 0，10/10 通过（断言：exit 与 expect 相等才 pass、相等但为 0 而期望 1 也 fail、无退出码但声明了命令 fail、正文里出现的 `(exit=n)` 不被误读）

## 不做范围

- 不做 git 集成与变更自动发现（当前项目无版本控制，任何 diff 推断都不可靠，见 standard.md 4.3）
- 不做 CI 流水线接入
- 不做多人协作的角色与权限模型
- 不做测试有效性校验（断言是否真在验东西，G3 查不出来，见 standard.md 9.4）

## 未验证

- **档位自评无外部约束**：声明 T0 就能少走卡点，没有第二人核对声明是否合理。这是体系的结构性缺口，本单元无法自我验证，只能靠偏离记录事后暴露（standard.md 9.1）。
- **跨项目泛化未验证**：目前只在 natdiag 一个真实模块上跑过，且该模块规模小、依赖少。对大型或强网络依赖的项目是否仍可持续，未取得证据。
- **长期遵守率未验证**：本规范刚建立，没有任何实际使用周期数据支撑「10% 开销上限」这一经验数值。
- **Windows 以外的平台未验证**：脚本路径分隔符与编码处理只在 Windows + Git Bash 下跑过。
