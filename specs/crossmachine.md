# crossmachine — 跨机测试包（P1 渲染与帧率）

## 目标

把「界面不卡」从**断言**变成**可跨机采集的数据**。

现状：M2a 的四条性能约束（seq 未变零回调、DOM 行数 ≤ 40、`transform` 而非 `width`、
零 `backdrop-filter`）全部在 jsdom 里判定。jsdom 没有排版引擎、没有合成器、没有 GPU，
它只能证明「DOM 结构对」，不能证明「60fps」。**这是全项目唯一一处「验过但没真验」的
结论**，而它恰好是用户能直接感知的那一项。

做法：产出一个**双击即开的单文件 HTML**，用真实浏览器渲染真实 `TorrentList` 组件，
跑三个场景，导出机器可读的 JSON。整个包不依赖 Python / Node / 网络，拷到任意
Windows 10/11 x64 机器都能跑。

## 关键设计决策

**测真实组件，不另写测试用的假列表。** 探针页面通过 Vite 第二入口引入
`src/components/TorrentList.tsx` 本体。另写一份「长得像」的列表，测出来的数字跟
产品无关 —— 那样连自己都骗不过。

**单文件自包含，双击可开。** 构建后把 `perf.html` 引用的 JS/CSS 全部内联成一个
文件。理由不是"好看"，是三个硬约束：`file://` 下 ES module 会被 CORS 拦（origin
为 `null`），跨机不能假设有 Node 起服务器，用户不该为了跑个测试去装任何东西。

**三场景而不是一个。** 单个「滚动时多少帧」的数字没法定位问题。拆开才能分辨：

| 场景 | 内容 | 分离出什么 |
|---|---|---|
| S1 静态 | 1000 条挂载，静置 1s | 基础渲染成本 + 有无持续动画在空转 |
| S2 纯滚动 | 1000 条，无数据更新，滚动 3s | 虚拟滚动与合成层开销 |
| S3 滚动+10Hz | 1000 条，10Hz 更新，滚动 3s | 数据更新对滚动的干扰 |

S2 好而 S3 差 → 问题在 setState 与重渲；S2 就差 → 问题在滚动实现或 CSS。
**只看 S3 一个数字，这两种情况分不开。**

**软渲染必须单独判，不能混进结论。** 虚拟机、远程桌面、无 GPU 的机器上浏览器走
SwiftShader 软件光栅化，任何页面都掉帧。通过 `WEBGL_debug_renderer_info` 取
renderer 字符串识别：命中则把环境标记为 `software`，帧率数据**只报事实、不参与
判定**。否则拿一台软渲染机器的数据回来，会把环境问题误判成代码缺陷。

**帧预算不能写死 60Hz。** 第一台真机（Intel Iris Xe，200% 缩放）三场景稳定 48fps、
0 掉帧、p50 20.8ms / p95 21ms，却被探针判成 `warn` —— 因为它按 60Hz 的 20ms 线来量，
而那块屏的帧间隔天然就是 20.83ms。**一个稳定的 48Hz 屏在 60Hz 的尺子下必然超线**，
这种误判会让真问题淹没在噪声里。

做法：挂载列表**之前**先在空页面上量 600ms 的空闲 rAF 间隔，取**中位数**（不是均值 ——
一次 200ms 的 GC 停顿会把均值拖低整份结果）换算刷新率，吸附到常见档位（24/25/30/40/48/
50/60/72/75/90/100/120/144/165/240，容差 5%），再由它推导全部阈值。

三个不能省的约束：

1. **校准必须在挂载任何东西之前。** 否则量到的是「这台机器跑这个页面有多快」，
   再拿它去给这个页面开脱 —— 自我循环论证。
2. **判定目标取 `min(60, 面板刷新率)`。** 面板低于 60 时按面板算（不然永远不可能及格）；
   高于 60 时不提高门槛（144Hz 屏上跑 60fps 不算缺陷，本项目的目标就是 60）。
3. **低面板不等于放行。** 另加一条与百分比无关的判据：中位帧间隔 > 1.5 × 帧预算即判 `fail`。
   48Hz 面板上稳定 24fps 的表现是「每隔一帧漏一个 vsync」，不是「面板限制」——
   没有这条，面板越差、判据越松，最该报的退化反而被吃掉。

结论里必须写明「显示器实测 XX Hz，阈值已按 XX Hz 缩放，绝对帧率不能与 60Hz 机器直接对比」。
少了这句，跨机数据会被当成同一把尺子量出来的。

**结论分三档，且必须带理由。** `pass` / `warn` / `fail` 之外还有第四种输出：
`env-limited`（环境受限，数据不可用于判定）。档位不是拍脑袋给的，每条都要写清
触发的是哪个阈值、实测值多少。

**帧统计口径写死在一处。** 分位数用线性插值；首帧 delta 丢弃（从 rAF 启动到第一帧
的间隔不是渲染耗时）；掉帧阈值 = 1.5 × 帧预算（60Hz 下 25ms）。这些口径如果在
页面里随手写，跨机数据就没法互相比。

**跨机结果靠人工回传，不做自动上报。** 页面导出 JSON 由用户拷回。
理由：测试包要能在隔离网络里跑；自动上报意味着这个包得带一个远端地址，
那它就不再是"零依赖"了。

## 实现期偏离（与批准版本的差异）

1. **探针用独立的 vite 配置构建，不走主应用的多入口。** 主应用若加第二入口，rollup 会
   拆出共享 chunk，内联成单文件后跨 chunk 的 `import` 语句无法解析（每个内联 `<script>`
   是独立模块作用域）。改 `vite.perf.config.ts`：单入口 + `codeSplitting: false`，
   产出恰好一个 JS 与一个 CSS。
2. **headless 验证改用 CDP 端口 + 页面 POST 回传，不用 `--dump-dom` / `--screenshot`。**
   原计划用 `--dump-dom` 读 DOM，实测在 Windows 上拿不到任何输出。原因有两层：
   `chrome.exe` 是 GUI 子系统程序、stdout 没接控制台；且这类「一次性任务」模式在本机
   启动后直接 `rc=0` 退出、什么都不产出。可靠做法是 `--remote-debugging-port=<port>`
   让浏览器常驻，由页面把报告 POST 回本地临时服务。
3. **不能靠 `Popen.poll()` 判断浏览器是否还活着。** Chrome 的启动器进程在 Windows 上
   会立即分离退出（`rc=0`），真正的浏览器进程是另一个 pid。原实现据此报「浏览器提前退出」，
   与事实完全相反。判据改为「CDP 端口能否应答」，并用 profile 目录名精确杀进程
   （不能杀所有 `chrome.exe` —— 用户自己的浏览器正在跑）。
4. **`collect-env.ps1` 强制纯 ASCII。** 与「UTF-8 无 BOM」的项目规范冲突，但 PowerShell 5.1
   会把无 BOM 的 UTF-8 按 ANSI（中文环境为 936）解码，中文注释的字节被误读后吞掉换行，
   把下一行赋值并进注释里。**这个失败是静默的**：脚本照常运行，只是 `driverDate` 和
   `remoteToolsRunning` 两个字段凭空消失。踩过一次，现已用断言锁住（AC-08 的第 ⑦b 项）。
5. **`MANIFEST.json` 的 `files` 不列自身，另用 `archiveEntries` 声明压缩包全集。**
   要求清单包含自己的哈希是不可能的自指。但压缩包里必须含清单（否则收到包的人无从核对），
   于是清单记录的「内容文件」与「压缩包条目」是两个集合，差值恰好是清单自己。
   这个差值不写出来就要靠人记，所以显式声明。
6. **`ScenarioDef` 的 `scrollMs` 拆成 `sampleMs` + `scroll`。** 原设计用 `scrollMs === 0`
   表示「不滚动」，同时又要表达「采样多久」，一个字段担两个语义；S1 的 1000ms 采样时长
   因此只能硬编码在页面里。拆开后三场景只共享同一段代码路径。
7. **帧率数据的分层判定加了一档。** 原设计 `pass/warn/fail` 三档，实现时加了 `env-limited`：
   软渲染环境下帧率由渲染器决定，任何页面都会掉帧，那份数据不该参与判定。
   另外 `collect-env.ps1` 的 `caveat` 分四档（`clean` / `virtual-display-present` /
   `remote-tool-running` / `remote-session`）—— 装了远程工具不等于正在被远程控制，
   一刀切成「不可信」会让提示失去意义。
8. **探针产物输出到 `desktop/dist-perf/`，不进 `desktop/dist/`。** 最初复用了 `dist/`，
   结果跑一次主应用的 `vite build`（`emptyOutDir` 为真）就把 `perf-standalone.html` 删了，
   表现为「打包脚本突然找不到文件」。两个构建目标不能共用输出目录，这条已在
   `inline_perf.py` 与 `t_perf_headless.py` 的注释里写明原因，避免以后有人「顺手合并」。
9. **压缩包做成可复现的（AC-09）。** 固定条目顺序、时间戳 `1980-01-01`、`create_system=0`。
   不做这一步，同一份输入在不同时刻压出的字节不同，sha256 只能证明「文件没被改」，
   证不了「这个包就是那次构建的」。测试里原样重打一次比对哈希，把这个性质锁住。
10. **目标机的安装要求写进清单，不只写进文档。** `target.installRequired` 是空数组，
    `target.prerequisites` 列出 Chrome/Edge 与 PowerShell 5.1+。结论是「零安装」，
    但结论本身要能被机器读到 —— 换机器时第一个问题就是「要装什么」。
11. **报告结构升到 `perf-v2`，阈值不再写死。** 批准版本里 `THRESHOLDS` 是常量
    （60Hz / 25ms / 40ms），真机数据证明这会把一块稳定的 48Hz 屏判成 `warn`。
    改动落在三处：`env.display` 记录实测刷新率、`thresholds` 变成按 `targetHz` 推导的结果、
    `summarizeFrames` 接受阈值参数（掉帧线随面板走，不再固定 25ms）。
    升 schema 而不是悄悄改口径 —— 旧数据（`perf-v1`）用旧尺子量、新数据用新尺子量，
    混在一张表里比较才是真的错。
    另外新增一条硬判据 `p50 > 1.5 × 预算`：**放宽门槛时必须同时加一条不放宽的线**，
    否则面板越差判定越松，最该报的退化会被吃掉。

## 本机实测结论（headless，不代表真机）

2026-11-03 复跑（加了刷新率校准之后），i7-12700 + Intel UHD Graphics 770，
1904×985 视口，Chrome 156，http 路径：

| 场景 | 帧数 | fps | p50 | p95 | 卡顿率 | 挂载 |
|---|---|---|---|---|---|---|
| S1 静态 | 60 | 59.99 | 16.7 | 16.8 | 0 | 7.1ms |
| S2 纯滚动 | 180 | 60.00 | 16.7 | 16.8 | 0 | 1.2ms |
| S3 滚动+10Hz | 180 | 60.00 | 16.7 | 16.8 | 0 | 1.0ms |

`display.source=measured`，`refreshHz=59.9` → 吸附 60 档 → `targetHz=60`，阈值与历史一致。

**和校准时之前的差异（59.04 → 59.99）要归因清楚：** 多出的 600ms 校准窗口顺带预热了
合成器，采样起点从「页面刚可见」变成「空转 0.6 秒后」，所以帧间隔从 17.0ms 变成 16.7ms。
**这不是加了代码优化**，只是量之前多等了一会儿。旧数字（59.04 / 58.90 / 59.00，
p50 17.00）是同一台机器的另一种起点，两者不能混在一张表里比较。

**读法**：这三行证明的是「探针跑通了、CSS 无违规、挂载成本几毫秒」，**不是**「真机 60fps」。
headless 的 rAF 由虚拟合成器驱动、实测 59.9Hz，它既不是真屏节拍，也测不出帧率余量 ——
一台真正跟不上的机器会掉到什么程度，只能看真机数据。

有价值的那一条是 **S3 与 S2 完全一致**：10Hz 全量快照更新没有拖慢滚动。
这是 M2a「seq 去重 + 外部 store」设计的第一个真实浏览器证据，此前只有 jsdom 里的
「监听器调用次数为 0」。

## 真机实测（第一台，2026-10-30，Intel Iris Xe · 200% 缩放）

| 场景 | fps | p50 | p95 | 掉帧 | 卡顿 |
|---|---|---|---|---|---|
| S1 静态 | 48 | 20.8 | 21 | 0 | 0 |
| S2 纯滚动 | 48 | 20.8 | 21 | 0 | 0 |
| S3 滚动 + 10Hz | 48 | 20.8 | 21 | 0 | 0 |

两次运行（间隔一分钟）数字几乎一致，说明可重复。

**这三行推翻了探针原来的判定，也是 AC-10 的由来。** p50 与 p95 只差 0.2ms、
两次运行 0 掉帧 0 卡顿 —— 分布是一条直线，每一帧都准时到。但旧版按 60Hz 的
20ms 线量，一块稳定的 48Hz 屏天然 20.83ms，必然超线，于是判了 `warn`。
**误判的代价不是难看，是真问题会被淹没**：每次都 warn 等于没有 warn。

按 AC-10 的口径（`targetHz=48`、p95 线 25ms、p50 线 31.25ms），这份数据判 `pass`，
理由里写明「显示器实测 48Hz，阈值已按 48Hz 缩放，绝对帧率不能与 60Hz 机器直接对比」。
**没有改任何样式代码** —— 变的只是尺子。

顺带成立的三条：
- **S3 = S2 = 48fps**：10Hz 全量快照更新不干扰滚动，M2a 的核心假设在真机（集显 + 200% 缩放）上成立
- `cssAudit` 为空：真实样式表在真实浏览器里也没有布局动画违规
- 这是一台 200% 缩放 + 集显的机器，跑满面板上限说明界面本身很轻

### 同一台机器复测（2026-11-03，`perf-v2`，浏览器全屏）

跑的是带刷新率校准的新包，浏览器 F11 全屏。两次间隔 5 分钟，字段取自两份 JSON：

| 运行 | 实测刷新率 | 命中档 | targetHz | S1/S2/S3 fps | p50 / p95 | 掉帧 | 挂载 |
|---|---|---|---|---|---|---|---|
| 08:48:26 | 48.1Hz（中位 20.8ms，29 样本） | 48 | 48 | 48 / 48 / 48 | 20.8 / 21.1 | 0 | 5.3 / 2.3 / 0.6ms |
| 08:53:35 | 47.8Hz（中位 20.9ms，29 样本） | 48 | 48 | 47.99 / 48 / 48 | 20.8 / 21.1 | 0 | 1.4 / 1.0 / 0.4ms |

两次 `verdict.level` 都是 `pass`，理由含「阈值已按 48Hz 缩放（帧预算 20.83ms）」。

**关键点：48 不是误判，是面板真实值。** 系统「设置 → 系统 → 屏幕 → 高级显示器设置」
显示 3120×2080、**48 Hz**、可变刷新率受驱动支持但已关闭。探针量到 47.8–48.1Hz，
与系统设置一致（偏差 < 1%）。这条把「校准量的是浏览器合成节拍，可能低于物理刷新率」
的疑点在本机上排除掉了 —— 至少这一台是一致的情形。

`mountMs` 比 10-30 那次低一个数量级（5.3→1.4 / 2.3→1.0 / 0.6→0.4），两次 11-03 运行之间
也有大幅波动（5.3 vs 1.4），说明这个数受 JIT 预热与磁盘缓存影响很大，**不能跨会话比较**，
只能在同一进程内比场景之间的相对差异。fps / p50 / p95 两次完全一致，说明帧采样本身稳定。

### 第二台真机（2026-11-03，i5-7200U + Intel HD 620 · 1366×768 @ 60Hz · 100% 缩放）

第一台是「好到顶」的机器（48Hz 面板 + 跑满），测不出下限。第二台是典型的低端笔记本：
双核四线程（`hardwareConcurrency=4`）、2016 年的低电压 U 系列、核显直连内屏、无缩放。

| 运行 | 实测刷新率 | targetHz | S1 | S2 | S3 | p50 / p95 | 掉帧 | 挂载 |
|---|---|---|---|---|---|---|---|---|
| 11:00:00 | 59.9Hz（中位 16.7ms，37 样本） | 60 | 60.00 fps | 60.00 fps | 59.67 fps | 16.7 / 16.8–16.9 | 0 / 0 / **1** | 15.7 / 4.7 / 3.9ms |
| 11:00:23 | 59.9Hz（中位 16.7ms，37 样本） | 60 | 60.01 fps | 60.01 fps | 60.01 fps | 16.7 / 16.8–16.9 | 0 / 0 / 0 | 3.3 / 3.0 / 2.3ms |

两次 `verdict.level=pass`，`cssAudit` 为空，`thresholds` 正确按 60Hz 推导
（预算 16.67ms、掉帧线 25ms、p95 线 20ms），与 48Hz 那台的 20.83 / 31.25 / 25 形成对照。

**这一台补上的三件事：**

1. **60Hz 档位的吸附在真机上成立**（59.9 → 60 档）。此前 60 档只有 headless 的虚拟合成器数据。
2. **「下限」有了第一个数据点**：四线程核显机、1000 行、边滚边 10Hz 全量换数据，仍然贴住面板上限。
   两台机器（48Hz 集显 / 60Hz 弱核显）都跑满，说明这个列表的渲染成本远低于一帧预算。
3. **`s3FpsDropMax` 这条判据第一次接近被触发**：11:00:00 那次 S3 有 1 帧间隔 33.3ms
   （= 漏一个 vsync），180 帧里 1 帧，掉帧率 0.56%，低于 `jankRatioMax` 1%，所以仍是 pass。
   **这是真实存在的一次漏帧，不是统计噪声** —— 记录在此，说明这套判据不是永远绿的橡皮章。

**一个环境坑（已写进 `crossmachine/RUN.md`）：** 这台笔记本用 HDMI「复制屏幕」接外接显示器时，
两个场景全部退化成 `Microsoft Basic Render Driver`（WARP），`verdict=env-limited`。
原因内屏接 HD 620、HDMI 接 RX 550，镜像要跨两块显卡同步合成。改「仅电脑屏幕」后恢复正常。
**软件光栅化下同样能测出 60fps 零掉帧**，但那组数据按规则不参与判定 —— 这条正好证明
「页面的环境自检是必要的」：不标出来，一份看起来完美的 WARP 数据会被当成真机结论。

## 不做范围

- **不做 WebView2 下的表现**（P2）。壳还没有，`specs/tauri-shell.md` 是它的前置。
- **不做跨机引擎互连**（P3）。需要两台机器人工配合，且要打包 `engine.exe`；本轮
  只解决「界面到底卡不卡」。P3 复用本包的产物结构，不重做。
- **不做 NAT 探测**（P4）。
- **不做帧率之外的性能指标**：内存占用、CPU 使用率、首屏时间不采。内存要看堆快照，
  单文件页面拿不到有意义的数；CPU 依赖机器，跨机不可比。
- **不做自动上报与结果聚合服务。**
- **不引 puppeteer / playwright。** headless 冒烟只需「打开 → 等 → 取一份 JSON」，
  为此拉一个带 Chromium 的依赖（~300MB）不划算，改用 Chrome 自带参数 + 页面 POST
  回传给本地临时服务器。

## 未验证

- **刷新率校准在三处验过：headless 59.9Hz、真机 48.1/47.8Hz（48 档）、真机 59.9Hz（60 档）。**
  30Hz / 50Hz / 120Hz 面板上「吸附是否命中正确档位」只有单测的合成样本，没有真机数据。
  这两个真机档位都是「实测值略低于标称值」的形态（59.9 vs 60.003、47.8–48.1 vs 48），
  吸附逻辑靠的正是那 5% 容差 —— 但它对「实测 29.4Hz 该吸到 30 还是 24」这类边界仍无证据。
- **校准量到的是「浏览器空闲时的合成节拍」，不一定是面板的物理刷新率。** 省电策略、
  驱动限制、窗口不是最前、外接屏由核显驱动等情形都会让节拍低于面板真实值，
  这时判定会**偏宽**（拿一个低节拍当门槛）。页面侧无法区分这两者 —— 只能靠人核对
  「设置 → 系统 → 显示 → 高级显示」里的刷新率是否与 `refreshHz` 一致。
  **2026-11-03 已核对一台：** 系统设置 48Hz，探针 47.8/48.1Hz，一致。
  仍未验的情形是「实际节拍低于面板」的那几种（电池模式、窗口被遮挡、外接屏），
  以及刷新率运行中变化（插电/电池切换）—— 后者会让后两个场景口径对不上，未做重测。
- **`perf-v2` 已在两台真机上跑过（48Hz 集显机、60Hz 弱核显机），仍是两台。** 第三台起才谈得上
  「跨机可比」；且两台都是「跑满面板」的机器，**没有一台真的跑不动** ——
  这意味着 `fail` 分支（`failFps`/`failP95Ms`）至今没有真机样本触发过，只有单测合成数据。
  换机后可能出现的问题仍集中在三处：目标机没有 Chrome/Edge、系统代码页非中文导致 ps1 行为差异
  （已用纯 ASCII 规避）、WebGL 被禁用导致 `renderer` 为 `no-webgl`。
  另外新增一条已踩过的坑：笔记本「复制屏幕」跨双显卡会让浏览器退回 WARP，见 RUN.md。
- **帧率与硬件的对应关系有两台基线，仍不足以判断「正常」。** 48Hz 屏 + Iris Xe 集显 + 200% 缩放、
  60Hz 屏 + HD 620 核显 + 100% 缩放，两台都跑满面板上限。问题在于**两台都没跑不动**，
  所以「p95 = 20ms 在另一台上算好还是坏」依然没有参照 —— 需要一台真的会掉帧的机器，
  或者用压力手段（放大到 10000 条）主动把帧率压下来，才能校准这条线。
- **`content-visibility: auto` 加在 `.list` 上疑似无效 —— 但已证明不重要。** `.list` 本身是滚动容器、
  永远在视口内，`content-visibility` 对它的屏外跳过优化无从生效；真正该加的是 `.row`。
  原本想靠 60Hz 机器验，结果第二台真机（i5-7200U + HD 620，四线程核显）**不加也是 60fps 零掉帧**，
  说明这条优化即便无效也没构成瓶颈。**结论：不必改**。真要改属于「省一点 GPU 余量」而非
  「修一个卡顿」，得单独一轮并在改前改后各采一次数据，且需要一台真能跑出掉帧的机器当标尺。
- **`reducedMotion` 开启时数据偏乐观。** 系统开了「减少动态效果」时 transition 被禁用，
  掉帧机会变少。页面会提示，报告里有 `env.reducedMotion` 字段，但还没分析过影响幅度。
- **只在 1000 条任务下测过。** 10000 条时虚拟滚动的 spacer 高度是 640000px，
  部分浏览器对超大元素的渲染有上限，未验证。
- **中位帧判据（p50 > 1.5 × 预算）的假阳性率未测。** 这条是硬判 fail 的，
  在一台本身有周期性卡顿（杀毒扫描、后台索引）的机器上是否会误伤，没有数据。
