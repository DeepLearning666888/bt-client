一、自动端口映射：三种协议全灭

上一轮只测了 UPnP，不够。自动映射共有三套协议，全部实测：

协议探测端点请求结果
UPnP IGD239.255.255.250:1900SSDP 组播 M-SEARCH0 响应
UPnP IGD192.168.1.1:1900SSDP 单播 M-SEARCH × 3 种 ST全部 timeout
UPnP IGD192.168.1.1:{80,443,8080,49152}9 条常见 IGD 控制路径无命中
NAT-PMP192.168.1.1:5351Opcode 0 · 请求外部地址timeout
NAT-PMP192.168.1.1:5351Opcode 1 · 映射 UDP 6881timeout
NAT-PMP192.168.1.1:5351Opcode 2 · 映射 TCP 6881timeout
PCP (RFC 6887)192.168.1.1:5351MAP · UDP 6881timeout

为什么这份结论可信

组播可能被拦，所以补做了单播 M-SEARCH 直连网关，三种 ST 全超时——排除组播干扰。NAT-PMP 与 PCP 共用 5351 端口，两条协议独立探测、各自超时——排除单协议实现问题。

网关 80 端口有 Web 管理界面，证明设备在线。所以结论是：路由器在线，但三个映射服务全部关闭，不是网络不通。

叠加上一轮的实测：12 个境外节点（8 国）回连两个端口，12/12 全部 Connection timed out；持 3.1 GB 已验证分片、159 个活跃连接时，上传 90 个采样全部为 0。

对产品的直接要求

这张网络下「自动入站」这条路彻底不通。但好消息是 NAT 本身是锥形 + 端口保持（5 个 STUN 服务器返回同一映射端口 50062，且等于本地源端口），意味着一旦手动映射成功，被动接入完全可用。

所以产品必须做两件事，且都不在 libtorrent 的能力范围内：

  • 入站诊断面板：明确告诉用户「未获得公网端口」，而不是让用户看到慢却不知道为什么。要显示：NAT 类型、检测到的公网 IP、三种映射协议的探测结果、回连测试结论。
  • 手动映射引导：给出「路由器型号 → 需要转发的端口 → 具体菜单路径」的可操作步骤。这是当前唯一可行的恢复上传能力的路径。

二、预分配策略：四个方案实测

Windows 上有四种方式给下载文件预占空间。这三个指标决定用户体验，且不受缓存干扰：

策略实现方式创建耗时立即占用磁盘需管理员
sparseFSCTL_SET_SPARSE + SetEndOfFile0.00 s0 GB否
reserveSetFileInformationByHandle(FileAllocationInfo)0.01 s4.00 GB否
zerofill全量写入 0 字节18.26 s4.01 GB否
validSetFileValidData0.00 s4.00 GB是 + 显式提权

测试条件：4 GB 名义文件，C 盘 NVMe（YMTC 238GB）。

零填充的代价被严重低估

18.26 秒写满 4 GB ≈ 224 MB/s，这个速度已经是这块盘顺序写的上限。按同样速度线性外推：

文件大小零填充耗时用户看到什么
4 GB（游戏安装包）18 秒转圈 18 秒
20 GB（高清电影）约 1.5 分钟进度 0%，无速度
60 GB（蓝光原盘合集）约 4.5 分钟进度 0%，无速度，大概率被当成卡死

绝大多数 BT 客户端默认就是零填充。这解释了为什么用户会觉得「点了下载没反应」。

吞吐对比数据不可用，原因写清楚

同一文件两阶段随机写（各 256 MB / 16KB 块）的结果看起来极为反常：

策略阶段 1阶段 2变化判断
sparse37.95 MB/s33.18 MB/s0.87×受缓存影响，偏低
reserve14.26 MB/s129.01 MB/s9.05×不可信
zerofill123.91 MB/s128.33 MB/s1.04×不可信
valid14.15 MB/s124.95 MB/s8.83×不可信

这套数字不能用。同一块盘、同样块大小，129 MB/s 已接近顺序写上限，随机 16KB 不可能达到。原因是页缓存：4 GB 文件在本机 68 GB 内存里被完全缓存，第二阶段覆盖写全部命中内存，根本没有落盘。

要拿到可信数字必须加 FILE_FLAG_NO_BUFFERING 做扇区对齐 IO。但这对产品决策没有影响——上一轮受控实验已经证明预分配不改变吞吐（aria2 五组配置包括 prealloc 全在 6.8~12.9 MB/s 波动，8 peer 乱序也能跑 119 MB/s）。

三、SetFileValidData 权限链：完整闭合

之前在 M0 计划里我写过「要么引导管理员安装授权，要么接受速度大幅下降」。这个判断错了，实测把链路走完：

步骤调用结果
1IsUserAnAdmin()True（有管理员令牌）
2PrivilegeCheck(SeManageVolumePrivilege)False ← 特权在 token 里但未启用
3SetFileValidData(h, size)失败，err 1314 = ERROR_PRIVILEGE_NOT_HELD
4AdjustTokenPrivileges(SE_PRIVILEGE_ENABLED)True（直接启用成功）
5PrivilegeCheck(SeManageVolumePrivilege)True
6SetFileValidData(h, size)SUCCESS

结论：这个 API 完全不需要

reserve（FileAllocationInfo）用 0.01 秒就真正占住了 4 GB 磁盘空间，不需要管理员，不需要任何特权，效果与 SetFileValidData 等价——都是「空间立刻被占住且不写零」。

SetFileValidData 唯一的额外能力是跳过 NTFS 的零填充标记，而 reserve 本来就不填充。所以：

  • 放弃 SetFileValidData。它带来一个严重安全问题：调用后文件区域内是磁盘上残留的旧数据（可能包含其他人或其他进程的敏感内容）。只要引擎有任何路径读取了未写入区域，就是信息泄露漏洞。MSDN 对此有明确警告。
  • 放弃「安装时申请管理员」这个产品难题。它是伪命题——不需要管理员也能做到最好的预分配效果。

这意味着最初担心的「UAC 会拦掉一批企业用户」这个问题，根本不存在。

决策点结论依据
