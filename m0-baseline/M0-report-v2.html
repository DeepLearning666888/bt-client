结论修正：上一版报告的判断是错的

v1 报告结论是「瓶颈在磁盘写入粒度（16KB）」。受控实验做完后，这个结论被实测数据推翻了。

反证很简单：同一个 aria2、同一块盘、同样是 15.7 KB 的单次写入，走 HTTP 顺序下载能跑到 262.91 MB/s；走 BT 单 peer 能到 103.08 MB/s； 8 peer 乱序反而更快，118.98 MB/s。如果 16KB 粒度真是瓶颈，这三个数字都不可能成立。

v1 之所以误判，是把「合成随机写测试的 7 MB/s」直接当成了 BT 的写入模式。实际上 BT 的写入是分块局部的 （即使 8 个 peer 也只是 8 条连续流），加上系统写缓存合并，远没到随机写的恶劣程度。合成测试测的是最坏情况，不是真实负载。

一、受控实验：把网络变量彻底拿掉

用本机 loopback 做传输，网络侧能力是 GB/s 级，不可能成为限制。同一个客户端、同一份数据（Debian 13.7 netinst，756 MB）， 只改变写入模式和落盘介质。

二、那互联网上的 8.58 MB/s 是什么限制的

互联网实测平均8.58MB/s
互联网峰值14.83MB/s
本机 BT 能力119.0MB/s
差距14×倍

同一台机器、同一个客户端，BT 在本机能做到 119.0 MB/s，接互联网只有 8.58 MB/s 平均 （最好的一次 5 秒均值到过 38 MB/s）。差的那 14 倍，是 seed 供给不足，不是我们的硬件或代码。

这条结论对产品规划的意义： 逐项调优客户端内部（磁盘调度、写缓存、预分配）在 SSD 上换不来速度，因为卡点根本不在客户端内部。 真正能拉开差距的是「拿到更多可用 peer」——连接数、NAT 穿透、tracker/DHT 覆盖、反吸血策略。 v1 报告里「磁盘调度是第一优先级」的判断，需要降级。

机械盘的随机 16KB 是 1.7 MB/s / 112 IOPS，112 IOPS 就是 7200 转的物理寻道极限。 这个数据是真的差，但 BT 实测没打到这个点——因为写入是局部的，机械盘的写缓存能吃下去。 残留风险：机械盘 + 上百个 peer + 高度碎片化的分片顺序，理论上仍可能触发寻道风暴，这一场景本轮无法在本地复现（最多只做到 8 个 peer）。

八、修正后的工程结论

  • 磁盘不是瓶颈（SSD 已证伪）。BT 写入块固定 16KB，但能跑到 103~119 MB/s。
  • 多 peer 乱序不是瓶颈。8 peer 比 1 peer 更快，不存在「peer 越多越慢」。
  • 互联网平均 8.58 MB/s 是种子供给限制。客户端内部调优换不来这块速度。
  • 真正该投入的方向：peer 获取能力。连接数上限、NAT/UPnP 穿透、DHT 覆盖、tracker 策略、反吸血。
  • 分片大小影响 CPU，不影响吞吐。16K 分片 CPU 65%，4M 分片 CPU 39~55%。自研引擎该用大分片省 CPU。
  • 机械盘仍是未排除的风险面。百级 peer + 机械盘的组合需要在真实种子上下补测。
  • 磁力首包 22 秒是确定要解决的问题。
下一步的技术验证应该换成：
  1. NAT 穿透成功率（公网端口可达性）——这是拉开速度差距的最大变量
  2. 真实种子下 HDD + 大 swarm 的写入表现
  3. 连接数上限对峰值速度的边际收益曲线
而不是继续在磁盘参数上做文章
