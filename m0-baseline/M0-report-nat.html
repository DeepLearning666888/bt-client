NAT 穿透与入站可达性实测

BT 下载客户端 · M0 技术验证第二轮 · 2026-10-27 · 测试机 192.168.1.100

一句话结论

这台机器的网络是锥形 NAT + 端口保持、公网 IP 真实——这是 BT 客户端能遇到的最好条件。 但路由器的 UPnP 是关闭的，所以端口映射无法自动建立；实测结果：12 个外部节点（8 国） 全部连不进来，上传速率为 0。客户端在这张网络上只能做「纯下载者」。

好消息是：下载速度没被拖垮——不靠入站也能跑到 11~17 MB/s、130+ 连接。 坏消息是：做种、PT 站保 ratio、稀有种子互助，全部失效。

一、测的是什么

BT 的速度由两个互相独立的因素决定：能主动连上多少 peer，和能被动接受多少 peer。 上一轮已经证明磁盘和 CPU 都不是瓶颈，互联网实测只有 8.58 MB/s 而本机 BT 能跑 119 MB/s， 差 14 倍。这一轮专门回答剩下那个变量：能不能被外面连进来。

方法上刻意避开「客户端自己说自己通了」——所有判断都以外部实测为准：

  • 用 STUN 直接观测 NAT 的映射行为，而不是听路由器描述自己
  • 用 SSDP 组播 + 单播两种方式找 UPnP 网关，绕开组播被拦的干扰
  • 起本地监听端口，让境外节点主动来连，看能不能连上
  • 量化代价：在无入站条件下测下载、上传、连接数

二、NAT 类型：最好的一档

同一个 UDP 套接字（本地源端口 50062）依次向 5 个不同厂商的 STUN 服务器发请求。 如果 NAT 是锥形，所有服务器应该看到同一个映射端口；如果是对称型，每个目标都会分到不同的端口。

STUN 服务器观测到的公网映射
stun.l.google.com203.0.113.7:50062
stun1.l.google.com203.0.113.7:50062
stun.cloudflare.com203.0.113.7:50062
stun.miwifi.com203.0.113.7:50062
stun.qq.comtimeout
stun.chat.bilibili.com203.0.113.7:50062

5 个服务器全部返回 203.0.113.7:50062，映射端口和本地源端口完全一致。 这叫 endpoint-independent mapping，也就是锥形 NAT，而且带端口保持。这是 UDP 打洞和端口映射最容易成功的一类 NAT。

为什么这条重要：锥形 NAT 意味着只要有一次成功的端口映射， 外部就能稳定连进来。它不是那种「怎么配都没用」的对称型 NAT。所以问题不在运营商， 在本机网络里某一个可用开关没打开。

还有一个更硬的限制：测量用的客户端本身不支持 UPnP

aria2 1.37.0 官方 Windows 构建没有编译 UPnP 支持：

所以这一轮无法验证「如果路由器开了 UPnP，自动映射能不能成功」。 这条不能算在 aria2 头上，但也确实没测到。

四、入站可达性：12 个节点全灭

在本机起 TCP 监听，然后请 6 个境外节点（每次）主动来连这个公网端口。分两个端口测： 一个是全新的 7001，一个是 BT 默认的 6881。

测试端口外部可达实际连进来的连接公开报告
no-mapping-fresh-port70010 / 6 可达0报告
bt-default-port68810 / 6 可达0报告

全部是 Connection timed out，不是 refused。这个区别有意义：refused 说明包到了机器上被拒绝， timeout 说明包在中间就被静默丢弃了——典型的 NAT 无映射行为。

必须说清的歧义：本机 Windows 防火墙三个配置文件全是启用状态。 所以「外部连不进来」是「NAT 没有端口映射」和「本机防火墙」两层叠加的结果， 单凭外部结果分不开两者各占多少。但结论不受影响——两种情况下被动接入都不可用。

但上传是彻底废的

上传0.000 MB/s
下载13.33 MB/s

测这个的时候我们已经持有 3.1 GB 验证过的分片、有 159 个活跃连接、 对端确实可能需要这些数据。结果：90 个采样，上传全部为 0，峰值也是 0。

因为没有任何 peer 能主动连我们，我们只能在我们自己发起的连接上顺带传一点； 而这些连接的对端要么已经拥有这些分片，要么在按 tit-for-tat 节流。

六、这对产品意味着什么

必须做的功能（不是加分项，是底线）

  • 自动端口映射：UPnP + NAT-PMP 都要做，并且要真的能验证成功，而不是「尝试过」
  • 可观测诊断：明确告诉用户「当前无法被动接入，速度可能受限」，并给出可操作指引 （开路由器 UPnP、或手动转发端口）。这条比任何调优都值钱——用户投诉最多的就是「一直 0 KB/s」却不知道为什么
  • uTP 打洞：这张网络是锥形 NAT，打洞成功率会明显高于对称型 NAT。libtorrent 有 BEP-55， 这是 ARIA2 完全不具备的能力

不能凭这一轮下的结论

这轮用的 aria2 是 TCP-only、无 uTP、无 UPnP/NAT-PMP 的客户端。 所以「被动接入不可用」只能说明这个客户端在这张网络上不行， 不能推出「libtorrent 方案也不行」。libtorrent 同时具备自动映射和 UDP 打洞， 在锥形 NAT 上这两个能力都值得实测——那是下一轮该做的事。

七、局限与未验证项

  • 本机防火墙的独立影响没测：三层防火墙全开，与 NAT 叠加，无法单独归因
  • aria2 的 UPnP 映射成功率无法测：该构建根本没有 UPnP 代码
  • uTP / UDP 打洞完全未测：aria2 不支持，这是最该补的一块
  • 只在一条网络上测过：结论描述的是「这条联通宽带 + 这台光猫/路由器」，不代表所有用户
  • 上传为 0 有第二种解释：该种子有 48~52 个做种者，对端可能本来就不缺数据。所以 0 是「与无入站一致」，但不足以单独证明因果
  • 写入放大没有稳定复现：本轮 180 秒测中出现 1.68 倍（19.13 写 / 11.37 下载）， 但随后可重复的测又是 1.0 倍左右，没找到触发条件，先记为待查
